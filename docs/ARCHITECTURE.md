# 架构与设计决策

## 分层

```
┌─────────────────────────────────────────────────────┐
│ index.html            语义化外壳（无逻辑）            │
├─────────────────────────────────────────────────────┤
│ app.ts                控制器：状态 + DOM 渲染 + 事件  │
├─────────────────────────────────────────────────────┤
│ ui/dom.ts             渲染原语（h / must / debounce） │
├─────────────────────────────────────────────────────┤
│ core/*                纯函数，零 DOM，全部可单测      │
│   api ← limiter ← retry                              │
│   cache · singleflight · compare · dedupe · answer   │
│   query · highlight · format · storage · types       │
└─────────────────────────────────────────────────────┘
```

**唯一的依赖方向是向下的。** `core/*` 不认识 DOM，也不认识 `app.ts`；所以限速、缓存、
退避、错误映射这些真正容易出错的地方，可以用毫秒级测试覆盖，而不需要浏览器。

## 一次搜索的时序

```
用户按 Enter
   │
   ├─ 1. buildQuery(text, filters)          "外贸 获客 site:zhihu.com after:2026-09-19"
   ├─ 2. cache.get(key = query|50) ──命中──▶ 直接渲染，花费不增加
   ├─ 3. singleflight.run(key)             ── 已有同 query 在飞？等它，不重复请求
   │        │
   │        └─ 4. bucket.take()            令牌桶排队（5/s），不是丢弃
   │                 │
   │                 └─ 5. fetch(api.deepseek.com)
   │                          ├─ 429/5xx/网络 → 退避重试（最多 2 次）
   │                          └─ 401/402/400 → 立即失败，附可操作提示
   │
   ├─ 5. 非空结果才写缓存（空结果缓存会让「搜不到」锁死 10 分钟）
   ├─ 6. renderResults / renderPager / renderStatus
   └─ 7. 历史 + URL 同步（?q=&site=&lang=&time=，可分享）
```

翻页完全在第 6 步之内：50 条已经在前端，`page` 变了只重渲染，不碰网络。

## 为什么是这些决策

### 静态、无后端

三个事实叠加（详见 README）：接口有 CORS、协议禁止 key 进客户端、限速与计费按账号。
BYOK 让「谁用谁付费」成为架构约束而不是运营策略。

### 令牌桶排队，而不是丢弃

超限的直接后果是 HTTP 429。丢弃会让用户以为「点了没反应」；排队则表现为「慢一点但一定出结果」。
对于 5 QPS、每次点击天然低于 1 QPS 的真实使用，排队几乎不可感知；对连点则完全消除 429。

### 同 query 合并（singleflight）

三个人在同一秒搜同一个词，只应该产生一次计费。`SingleFlight` 用 key 到 Promise 的映射做到这一点，
失败时清空槽位以便重试。

### TTL + LRU，且空结果不入缓存

热门词命中缓存是零成本零延迟；但**空结果**是特例：它可能只是索引暂时没收录，
缓存 10 分钟等于把「搜不到」当成事实固化下来。所以空结果一律不写缓存。

### 先转义，再加 `<mark>`

搜索结果是与用户输入无关的第三方文本。`highlight()` 的做法是：先把整段文本 HTML 转义，
再在被转义后的字符串上用正则加 `<mark>`。这样任何结果内容都不可能变成标签——e2e 里有一项检查
就是断言渲染后的 DOM 里不存在来自结果的 `<script>`。

### 存储带版本信封

`{ v: 1, d: <value> }`。版本不匹配时静默丢弃旧值而不是崩溃；`localStorage` 不可用
（隐私模式、`file://`、配额耗尽）时降级为内存，并在设置里显示「内存（刷新即失效）」。

## 错误分类

| kind | 触发 | UI 文案 | 重试 |
| --- | --- | --- | --- |
| `auth` | 401、或未设置 key | Key 无效，去设置里换 | 否 |
| `payment` | 402 | 余额不足，去充值 | 否 |
| `forbidden` | 403 | 被安全策略拒绝 | 否 |
| `rate` | 429 | 触发限速，本页会自动排队重试 | 是 |
| `timeout` | 25s 超时 | 网络不稳定 | 是 |
| `network` | fetch 抛错 | 检查网络/代理 | 是 |
| `server` | 5xx、非法 JSON、缺字段 | 服务端错误 | 是 |
| `bad-request` | 400 / 404 | 请求不合法 | 否 |
| `aborted` | 新搜索取消旧搜索 | 静默丢弃 | — |

重试策略：`600ms × 2^n + jitter(0–300ms)`，最多 2 次；只有 `rate/server/network` 参与重试。

## 去重层（dedupe.ts）

只做一件事：不让人看到同一篇文章的多个副本。

- **语言克隆**：去掉 `/zh-cn/` `/ko/` 前缀后 URL 相同即视为同一页。内容农场最典型的手法
  就是一篇文挂十几个语言版本，实测一次查询能去掉 2 条。
- **同标题**：归一化大小写/标点/空格后比较。
- **保留全部域名多样性**：不做同域数量限制，也不重排。顺序是接口的判断，客户端没有
  更强的依据（见下面「被删掉的东西」）。
- 提供 `dedupeBlocklist` 但默认空：屏蔽某个站点是价值判断，应该由部署者决定。

## 答案层（answer.ts）

检索是原料，答案是产品。第二次调用把 8 条摘要合成一段带引用的答案：

```
buildMessages(query, results)  →  system: 只依据资料、标注 [n]、不超过 200 字
                                   user:   问题 + 编号资料（每条 ≤420 字摘要）
streamAnswer()                 →  SSE 逐块解析，delta 直接喂给 DOM
citationIndexes(text, n)       →  取出 [n]，越界的丢掉（防止死链）
```

放在 `core/` 而不是 UI 里的原因：SSE 分块、`
` 归一、`[DONE]` 提前终止、
畸形 payload 跳过——这些全是边界条件，必须有测试，而测试不该开浏览器。

失败语义是刻意设计的：**摘要失败不影响搜索**。卡片显示错误与原因，列表照常可用；
用户可以「停止」「收起」，或直接在设置里关掉摘要。

## 被删掉的东西（以及为什么）

0.3 里我实现过一层「重排」：`0.6×相关度 + 0.25×权威 + 0.15×时效` 重新打分，
外加同域第 3 条降权。跑 10 查询基准后删了：

```
唯一域 8.2 → 8.3      中位分 1.86 → 1.84
```

收益在噪声范围内，代价却是把接口的排序换成我的排序。**没有数据支撑的排序偏好不该留在
代码里**——它增加了理解成本，还让「为什么这条排前面」变得无法回答。保留的只有去重，
因为「同一篇文章出现三次」是客观错误，不是偏好。

## 对比模式## 对比模式

一次输入 → 四个站内查询，四栏并排：

```ts
compareQueries('rust', filters, presets)
// → ['rust site:zhihu.com', 'rust site:github.com', …]
```

三个刻意的取舍：

1. **用户自己的 `site:` 筛选被丢弃**，否则四栏会是四次相同查询；
   排除站点、语言、时间仍然作用到每一栏。
2. **每栏独立缓存、独立计费**：`cache` 的 key 是各自的 query，某栏命中缓存
   就只省那一栏的钱。状态栏按「实际发出的请求数」算钱，不是按栏数。
3. **只取 10 条/栏，不分页**：对比是「看一眼哪站有货」，不是精读；
   点「只看 zhihu.com」才切回单栏继续分页。

渲染上，对比模式会把外壳从 880px 放宽到 1200px，让四栏在笔记本上一行排开
（`body[data-mode='compare']` 控制），窄屏自动降到 1 栏。

## PWA 缓存规则

service worker 只有一条硬规则：**只碰同源 GET**。

| 请求 | 策略 | 原因 |
| --- | --- | --- |
| 页面导航 | 网络优先，失败回退缓存的壳 | 重新部署后刷新即可见 |
| `/assets/*`（带 hash） | 缓存优先 | 文件名随内容变，不存在陈旧问题 |
| `api.deepseek.com/*` | 完全不介入 | 搜索结果属于用户，绝不进共享缓存 |

## 可选代理

`server/proxy.mjs` 用 190 行解决「不想让用户填 key」这件事，两种模式：

- **BYOK 转发**：不设 `DEEPSEEK_API_KEY`，原样转发客户端的 `Authorization`。
  你获得统一域名/日志/限流，但不碰账单。
- **共享 key**：设了 `DEEPSEEK_API_KEY` 就注入服务端 key，你付钱。
  此时 5 QPS 是全站共享的，代理必须排队：`createPacer()` 把请求按 `1000/qps`
  毫秒错开，排队超过 `maxWaitMs` 直接回 429 而不是无限堆积。

代理不做身份体系——那是网关层的事，README 的「已知限制」里写明了。

## 扩展点

- **换搜索供应商**：实现 `SearchApi` 的形状即可（`search()` / `fetchPage()` 返回同一套类型）。
- **加后端代理**：设置里的「搜索端点」已经支持覆盖；写一个转发到 DeepSeek 的网关，
  把 key 收在服务端，前端只需改端点。
- **多引擎对比**：`buildQuery` 支持 `site:` 组合，并发多个 query 用 `SingleFlight` 分开即可。
- **换框架**：`core/*` 与框架无关；只有 `app.ts` 和 `ui/dom.ts` 需要重写。
